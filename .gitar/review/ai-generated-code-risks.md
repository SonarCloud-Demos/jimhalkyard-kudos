# AI-generated code risks

## Scope

This guidance applies to all code changes, with particular attention to changes that exhibit patterns common in AI-generated code: boilerplate-heavy, repetitive, inconsistent with repository conventions, or containing placeholder patterns.

## What to flag

Flag these AI-generated code defects and cite the concrete consequence:

- **Invented APIs or packages**: imports, function calls or package references that do not exist in the dependency tree, standard library or repository. Consequence: compilation or runtime errors, broken builds.

- **Dead code**: functions, classes or branches that are defined but never called, or unreachable code after unconditional returns or breaks. Consequence: maintenance burden, false confidence in coverage, misleading future developers.

- **Duplicated code**: near-identical functions or logic blocks that differ only in variable names or minor details, suggesting copy-paste without abstraction. Consequence: maintenance burden, bug fixes applied inconsistently.

- **Over-broad exception handling**: catch blocks that catch all exceptions (such as `catch (Exception)`, `except:`, `catch { }`) without re-throwing, logging specific error types or justifying the breadth. Consequence: silent failures, difficulty debugging production issues.

- **Placeholder stubs shipped**: functions that return hardcoded values, raise "not implemented" errors, or contain TODO comments indicating incomplete implementation. Consequence: incorrect behaviour in production, unfinished features shipped.

- **Scope creep**: changes that go beyond the stated PR description or linked issue, adding unrelated features, refactoring unrelated code or changing behaviour not mentioned in the rationale. Consequence: harder review, unintended side effects, unclear intent.

- **Convention departures**: code that does not follow repository conventions (naming, error handling patterns, project structure, idioms) without justification. Consequence: inconsistent codebase, maintainability issues, harder onboarding.

## Evidence required

Before flagging:

- Verify the API or package does not exist by checking imports, dependency manifests or standard library documentation.
- Confirm dead code is not called by searching for references in the repository (including tests, scripts and configuration).
- Check whether the duplicate code is intentional (similar but semantically different, or required by framework patterns).
- Verify the scope creep is not justified in the PR description, commit messages or linked issue.

## Exceptions

Do not flag:

- **Intentional boilerplate**: code required by frameworks, compliance with interface contracts or scaffolding generated by tools.
- **Defensive error handling**: broad exception handling in top-level handlers, CLI entry points or framework integration points where fine-grained handling is not possible.
- **Experimental or prototype code**: changes explicitly marked as proof-of-concept, spike or experimental in the PR description.
- **Style differences**: minor naming or formatting differences that do not affect correctness or violate documented conventions.

## What NOT to flag

Do not comment on:

- Code style, naming or formatting differences that are not inconsistent with repository conventions.
- Generic advice to "avoid AI-generated code" or "review carefully" without citing specific defects.
- Hypothetical risks or concerns about AI use without concrete evidence of a defect in the diff.
- Code that is verbose or less elegant than hand-written code, but correct and consistent with the repository.
